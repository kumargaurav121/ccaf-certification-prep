CCAR-F Exam Blueprint

Everything the exam measures, on one page. Every claim here is taken directly from the official Exam Guide v1.0 — this is the map you revise against.

Exam code CCAR-F Items 60 Time 120 min Pass 720 / 1000 Fee $125 Valid 12 months

Logistics

ItemDetail
FormatMultiple-choice and multiple-response. Each item states how many to select.
Structure4 scenarios drawn at random from a bank of 6.
DeliveryPearson VUE — online proctored or test centre. Closed book, no notes, no AI.
ScoringCriterion-referenced, scaled 100–1000. Cut score 720. Set by a formal standard-setting study.
ReportingPass/fail + scaled score + percent correct by domain. Domain percentages are informational only — the total scaled score decides.
Retakes14 days after 1st fail, 30 after 2nd, 90 after 3rd. Max 4 attempts / rolling 12 months. Fee each time.

IDGovernment photo ID; name must match registration exactly.
RenewalFree non-proctored assessment before the 12 months lapse. Lapse = full exam at full fee.
The structural fact that matters most

Because only 4 of 6 scenarios appear, you cannot game the exam by mastering one scenario. But the six scenarios map onto a small set of recurring architectural decisions — learn the decisions, and every scenario is the same exam.

Domain 1 — Agentic Architecture & Orchestration

27%7 task statements · ≈16 items
  • TS 1.1Design and implement agentic loops for autonomous task execution. Continue on stop_reason: "tool_use", terminate on "end_turn". Append tool results to history.
  • TS 1.2Orchestrate multi-agent systems with coordinator–subagent (hub-and-spoke) patterns. Dynamic subagent selection, scope partitioning, iterative refinement loops.
  • TS 1.3Configure subagent invocation, context passing, and spawning. Task tool, allowedTools must include "Task", explicit context, AgentDefinition, parallel spawning.
  • TS 1.4Multi-step workflows with enforcement and handoff. Programmatic prerequisite gates vs prompt guidance; structured escalation handoffs.
  • TS 1.5Apply Agent SDK hooks for tool call interception and data normalisation. PostToolUse for normalising results; interception for blocking policy violations.
  • TS 1.6Design task decomposition strategies. Fixed prompt chaining vs dynamic adaptive decomposition; per-file + cross-file review passes.
  • TS 1.7Manage session state, resumption, forking. --resume <name>, fork_session, and when a fresh session with an injected summary beats resuming stale context.

Domain 2 — Tool Design & MCP Integration

18%5 task statements · ≈11 items
  • TS 2.1Design tool interfaces with clear descriptions and boundaries. Descriptions are the primary tool-selection mechanism; eliminate overlap; split generic tools.
  • TS 2.2Implement structured error responses. MCP isError; errorCategory (transient / validation / business / permission), isRetryable.
  • TS 2.3Distribute tools across agents and configure tool_choice. Too many tools degrades selection; scoped access; "auto" / "any" / forced.
  • TS 2.4Integrate MCP servers. Project .mcp.json vs user ~/.claude.json; ${ENV_VAR} expansion; MCP resources as content catalogs.
  • TS 2.5Select built-in tools: Read, Write, Edit, Bash, Grep, Glob — Grep for content, Glob for paths, Read+Write when Edit's anchor isn't unique.

Domain 3 — Claude Code Configuration & Workflows

20%6 task statements · ≈12 items
  • TS 3.1CLAUDE.md hierarchy: user (~/.claude/CLAUDE.md), project, directory. @import for modularity; .claude/rules/; /memory to diagnose.
  • TS 3.2Slash commands and skills. .claude/commands/ (project, versioned) vs ~/.claude/commands/; SKILL.md frontmatter context: fork, allowed-tools, argument-hint.
  • TS 3.3Path-specific rules. .claude/rules/ with YAML paths: globs — beats directory CLAUDE.md when files are spread across the tree.
  • TS 3.4Plan mode vs direct execution. Plan for architectural/multi-file/multi-approach; direct for well-scoped single changes. Explore subagent for verbose discovery.
  • TS 3.5Iterative refinement. Concrete I/O examples, test-driven iteration, the interview pattern; batch interacting fixes, sequence independent ones.
  • TS 3.6CI/CD integration. -p/--print, --output-format json, --json-schema; CLAUDE.md as CI context; independent review instance.

Domain 4 — Prompt Engineering & Structured Output

20%6 task statements · ≈12 items
  • TS 4.1Explicit criteria to raise precision. Categorical criteria beat "be conservative" / "only high-confidence". False positives destroy developer trust.
  • TS 4.2Few-shot prompting. 2–4 targeted examples for ambiguous cases; show reasoning; generalises to novel patterns; reduces extraction hallucination.
  • TS 4.3Structured output via tool_use + JSON schema. Eliminates syntax errors, not semantic ones. Nullable fields prevent fabrication; enum + "other"/detail for extensibility.
  • TS 4.4Validation, retry, feedback loops. Retry with the specific validation error. Retry fails when the information is simply absent from the source.
  • TS 4.5Batch processing. Message Batches API: 50% cheaper, ≤24 h, no latency SLA, custom_id correlation, no multi-turn tool calling. Never for blocking workflows.
  • TS 4.6Multi-instance / multi-pass review. An independent instance beats self-review; per-file passes + a cross-file integration pass beat one big pass.

Domain 5 — Context Management & Reliability

15%6 task statements · ≈9 items
  • TS 5.1Preserve information across long interactions. Persistent "case facts" block; trim verbose tool output; mitigate lost in the middle by position-aware ordering.
  • TS 5.2Escalation and ambiguity. Escalate on explicit request, policy gap, or no progress. Sentiment and self-reported confidence are not valid triggers. Multiple matches → ask, don't guess.
  • TS 5.3Error propagation across agents. Structured error context; distinguish access failure from valid empty result; never silently suppress, never kill the whole workflow.
  • TS 5.4Large codebase exploration. Scratchpad files, subagent delegation, summarise-then-spawn, crash-recovery manifests, /compact.
  • TS 5.5Human review & confidence calibration. Aggregate accuracy hides per-segment failure; stratified sampling; field-level confidence calibrated on labelled sets.
  • TS 5.6Provenance & uncertainty. Claim–source mappings survive synthesis; annotate conflicts rather than picking one; carry publication dates; render by content type.

In scope vs out of scope

The guide lists these explicitly. Anything on the right is wasted study time.

Tested

  • Agentic loop control flow, stop_reason
  • Coordinator–subagent orchestration, parallel Task calls
  • Explicit subagent context passing, crash manifests
  • Tool description quality; split vs consolidate
  • MCP tools vs resources; project vs user scope
  • Structured errors; transient/business/permission
  • Escalation criteria and policy gaps
  • CLAUDE.md hierarchy, @import, rules globs
  • Commands & skills scope + frontmatter
  • Plan mode vs direct execution
  • Iterative refinement patterns
  • tool_use schemas, tool_choice, nullable fields
  • Few-shot for ambiguity and false positives
  • Batch API suitability, custom_id failure handling
  • Context trimming, fact extraction, input ordering
  • Confidence calibration, stratified sampling
  • Claim–source mappings, temporal data, conflicts

Not tested — skip

  • Fine-tuning / training custom models
  • API auth, billing, account management
  • Language/framework implementation detail
  • Deploying or hosting MCP servers
  • Claude's internal architecture / weights
  • Constitutional AI, RLHF, safety training
  • Embeddings, vector databases
  • Computer use / browser automation
  • Vision and image analysis
  • Streaming, server-sent events
  • Rate limits, quotas, pricing math
  • OAuth, key rotation, auth protocols
  • AWS / GCP / Azure specifics
  • Benchmarking, model comparison
  • Prompt caching implementation (know it exists)
  • Tokenisation / token-counting algorithms
