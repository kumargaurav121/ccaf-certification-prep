The rule that catches all five

When an option's appeal is that it avoids friction — keeps working, keeps helping, keeps the feature on, picks a winner so nobody has to see a conflict — be suspicious. The exam treats friction as information. A failure is a fact to report. A conflict is a finding to surface. A refusal is an instruction to obey. Smoothing any of them over hides the truth from whoever decides next.

2. Escalation: the signal decides, not the issue

On Mock 2 you escalated an angry customer with a routine issue (too eager). On Mock 3 you kept working on a customer who explicitly asked you to stop (not eager enough). Opposite errors, one cause: you're judging the issue ("this looks routine") when the exam wants you to classify the signal.

Which door is this? Not sentiment (they're not angry, they're clear). Not a policy gap. It is door #1: an explicit request for a human — and door #1 is unconditional. The issue being routine is irrelevant; the customer closed the case to the agent.

What you picked, from the customer's chair: "I said don't work on it. The bot said 'understood' and then… went and looked up my order anyway. It didn't listen." Investigating "for the handoff" is working the case. Trust damage is the same.
Correct, from the customer's chair: "I asked for a human and got one." The human can gather details themselves. Obeying costs you nothing; overriding costs trust.

3. "Degrade gracefully" is the trap's costume

You picked "return empty results marked as success when a search fails, so downstream degrades gracefully instead of halting." That phrase — degrade gracefully — is good engineering vocabulary wrapped around the single worst anti-pattern in the blueprint: silent suppression.

Real example — what downstream actually believes

Search for: "EU battery recycling regulations 2026"
Reality:    the search API timed out.

Option A (yours):  returns  { results: [], status: "ok" }
  → synthesis agent believes: "there are no EU battery regulations"
  → final report states it as fact. Nobody knows a search broke.

Option B+E (correct):  local retry ×2 fails →
  returns { error: "timeout", attempted: "EU battery recycling 2026",
            partial: [3 sources from first page], isError: true }
  → coordinator: retry with different phrasing, or proceed and
    annotate "EU regulations: coverage gap, source unavailable"

"Gracefully" hid the fact that a report now contains a false negative it cannot doubt. Halting isn't the alternative — that's the other anti-pattern (option C). The middle is the ladder: recover locally → propagate structure with partials → let the coordinator decide → annotate gaps.

4. Conflicts are information — and dates dissolve most of them

You correctly chose "annotate both values" but paired it with "rank by credibility and report only the higher" — which is the same silent selection as "pick the larger number", with a credibility veneer. You missed the second correct answer: require dates.

Real example — why dates matter more than credibility

Source A (Gartner):     "EV battery market: $4.2B"
Source B (McKinsey):    "EV battery market: $5.1B"

Without dates → looks like a conflict → someone "picks the credible one"
With dates    → A is a 2024 figure, B is 2026.  Not a conflict at all:
                the market grew. Both are correct.

Structured output the subagent SHOULD return:
{ claim: "$4.2B", source: "Gartner", collected: "2024-Q3" }
{ claim: "$5.1B", source: "McKinsey", collected: "2026-Q1" }
{ conflict_detected: true, note: "figures from different years" }

Credibility ranking would have thrown away a correct figure. Dates turned an apparent contradiction into a trend. That's why the blueprint makes dates a structural requirement (TS 5.6), not a nice-to-have.

7. Two facts to pin down

Batch API — what it can and cannot do

✓ include tool definitions in requests
✓ return tool_use blocks in results
✗ EXECUTE a tool and CONTINUE mid-request
  (that needs a live loop; a batch is
   one request → one response, done)
✗ any completion-time guarantee
  (no SLA, at any hour — up to 24h)
✓ results matched by custom_id
✗ results matched by position/order

You picked "supports multi-turn tool calling." It returns the request for a tool; nobody is there to run it and send the result back. That's the whole reason it can't do agentic work.

isError — envelope vs payload

YOUR PICK — structured, but still "success":
{ content: [{ type:"text",
    text: '{"error":"could not parse"}' }] }
→ agent sees a SUCCESSFUL result whose
  text happens to contain an error. It
  may treat it as document content.

CORRECT — flag on the envelope:
{ content: [{ type:"text",
    text: '{"errorCategory":"validation",
            "isRetryable":false, ...}' }],
  isError: true }
→ machine-recognisable failure. THEN the
  structured payload guides recovery.

L06's lesson was "structure the error" — you did. But structure goes inside a result whose envelope already says isError: true. Both layers.
