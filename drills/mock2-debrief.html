2. The mental model that fixes most of Domain 1

Five of your seven D1 misses come from one fuzzy picture: what a subagent can and cannot see. Here is the model in one analogy.

Real life

You're a project manager. You hire a freelancer and email them a brief.

The freelancer cannot see your inbox — not your other emails, not what other freelancers are doing, not your earlier notes. They have only the brief you sent.

If you want them to use research another freelancer did, you must attach it to the brief. "Use the findings from before" means nothing — they never saw "before".

When they finish, they email you one deliverable. You read it. They don't email each other; everything goes through you.

Agent SDK

You're the coordinator. You spawn a subagent via the Task tool with a prompt string.

The subagent starts with a fresh context — no parent conversation, no parent tool results, no sibling output. It has only its system prompt + the Task prompt.

To give it another agent's findings, you must paste them into the Task prompt. "Use the sources found" means nothing — it never saw them.

It returns one final message to you. Subagents never talk to each other; hub-and-spoke routes all of it through the coordinator.

sealed contexts · one channel in (the brief) · one message out · no sibling wires

Now watch all five misses dissolve into this one picture:

Q13 — "coordinator won't delegate." You picked "the subagents' tools array blocks it." But hiring the freelancer at all needs permission: the Task tool must be in allowedTools. No permission to hire → the manager quietly does the job themselves. A tools array just limits what the freelancer can do once hired.
Fix: "coordinator won't spawn subagents" → first check allowedTools includes "Task".
Q14 — "synthesis has no findings." You picked "its context filled and evicted them." But it was never given them — the freelancer wasn't emailed the research. Nothing to evict; the brief simply didn't contain it. Context isn't silently dropped after spawn.
Fix: "subagent ignored prior findings" → the coordinator didn't paste them into the Task prompt. Always the first suspect.
Q17 — "run them in parallel." You picked "set parallel:true on each agent." That flag doesn't exist. Parallel = mail all three briefs in the same outgoing batch: emit all three Task calls in one coordinator response.
Fix: parallel subagents = multiple Task calls in a single turn (same mechanic as parallel tool calls). One-per-turn is accidentally sequential.
Q60 — "why route through the coordinator?" You picked "direct messaging isn't supported." The reason is a design choice, not a technical limit: routing through the manager gives observability, consistent error handling, and controlled information flow — the manager decides what each freelancer sees.
Fix: hub-and-spoke exists for observability + error handling + controlled flow. (It costs more tokens, not fewer — you pay that for control.)

3. Two more D1 concepts, made concrete

Q54 · Fixed chain vs adaptive

The test: can you list the steps before you start?

Yes → fixed prompt chain. "Check formatting, then citations, then facts" — you know all three aspects up front. A fixed sequence of focused passes: predictable, testable, and it dodges the attention-dilution of one big combined pass.

No → adaptive. "Add tests to a legacy codebase" — the next step depends on what you discover. You picked adaptive for the review, but its aspects were known in advance. Known list → chain.

Q59 · What a session stores

A session saves the conversation, not the files. Resume it and you restore what the agent knew — every old tool result — not what the code is now.

So a week-old resume replays stale reads: it "remembers" function signatures that no longer exist, and has no reason to doubt them. You picked the exact opposite ("sessions restore the old filesystem") — that's backwards.

Fix for stale results: start fresh, inject a short summary of the conclusions that are still true, let it re-read the rest.
