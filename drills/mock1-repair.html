1. The tools themselves — what each one actually is

You use these daily through Claude Code, but the exam tests whether you can name what each does mechanically. Two of them search, three of them change files, one runs anything.

The two searchers

Grep searches the CONTENT inside files, using regular expressions built-in

Named after the classic Unix tool (global regular expression print). You give it a text pattern; it scans through the lines of text inside files and returns every file (and line) where the pattern occurs. It never cares what a file is called — only what is written in it.

Grep  pattern: "calculateRefund\("        → every file whose text contains a
                                            call to calculateRefund
Grep  pattern: "TODO|FIXME"               → every line with either marker
Grep  pattern: "import .* from 'legacy'"  → every import of the legacy package

Reach for it when the question is about what code says: "who calls this function?", "where is this error message produced?", "which files import X?"

Glob matches file PATHS against a wildcard pattern — never opens the files built-in

A "glob" is the wildcard language of file paths. * matches anything within one directory level; ** matches across any depth of directories; {a,b} tries both alternatives. Glob answers "which files exist with names like this" — it reads nothing.

**/*.test.tsx        → every .test.tsx file, anywhere in the tree
src/**/*.{ts,tsx}    → all TS/TSX under src/, any depth
*.md                 → markdown files in the current directory only
src/components/*.tsx → components at exactly that level (one *  = no recursion)

Reach for it when the question is about what files are called: "find all test files", "list every YAML config", "are there any .env files here?"

The exam's favourite discrimination: "find all callers of formatCurrency" is a content question → Grep. "find all test files" is a naming question → Glob. Same lesson stem, opposite answers.

The three changers

Read → Write load a whole file · write a whole file the recovery pair

Read loads a file's full contents into context. Write replaces the entire file with new content. Together they are the blunt instrument: read everything, produce the complete modified text, write everything back. Wasteful for small changes — but immune to the anchor-uniqueness problem below, which is why they are the documented fallback.

Edit surgical replacement: find this exact string, replace with that string preferred for targeted changes

Edit takes an old_string and a new_string. It finds the old text and swaps in the new — sending only a diff, not the whole file. The catch that generates exam questions: the old string must identify ONE place. If it occurs twice, Edit cannot know which you meant, so it fails rather than guesses — a safety feature.

File contains:            timeout: 30        ← line 12
                          timeout: 30        ← line 48
                          timeout: 30        ← line 95

Edit old_string="timeout: 30"  →  ✗ FAILS: non-unique match
                                   (refuses to guess which one)

Two ways forward, for two different intents:

  • You wanted all of them changed → re-run Edit with replace_all: true. One call, every occurrence.
  • You wanted one of them changed → the anchor can't discriminate, so fall back to Read + Write: load the file, change the right line, write it back.

Bash + sed what you actually reached for — twice always the distractor

Bash runs arbitrary shell commands — legitimate for tests, builds, git. sed ("stream editor") is a 1970s Unix tool that rewrites text as it streams through: sed -i 's/userData/customerData/g' file.ts means "in place (-i), substitute (s/) every (/g) match". It works — in your terminal. The exam scores it wrong every time, for stated mechanical reasons:

  • The pattern is a regex whether you meant it or not. Innocent-looking text is full of live metacharacters: in s/config.timeout/x/ the dot matches any character, so configXtimeout also matches. Edit matches literally.
  • No uniqueness guard. sed happily changes all three timeout: 30 lines when you meant one — precisely the mistake Edit's failure exists to prevent.
  • Silent no-op. If the pattern matches nothing, sed exits successfully having changed nothing. Edit tells you it failed.
  • Line-number addressing is brittle — the moment an earlier edit shifts the file, sed '48s/…' points at the wrong line.

The habit worth keeping from this: your terminal instincts are optimised for you, not for the exam's doctrine. Catalogue so far: sed → Edit doctrine · Agent → answer Task · stdin tricks → answer -p.

3. The seven leaked patterns — re-armed properly

Each of these was taught in L02–L08 and lost on the mock. For each: the principle, and the concrete situation the exam wraps it in.

TS 1.5 Hooks vs prompts — and which hook

Principle: anything that must happen every time, identically is code, not persuasion. A prompt instruction has a failure rate; a hook does not. Then pick the hook by lifecycle position: PreToolUse fires before execution (block or rewrite the call — policy gates, thresholds); PostToolUse fires after (transform the result — normalisation).

Exam wrapper: "three backend tools return dates/money/status in three formats and the agent misreads them." Format conversion is deterministic → hook, and there's nothing to transform until the tool has returned → PostToolUse with updatedToolOutput. A system-prompt conversion table is the polished-sounding wrong answer.

TS 1.6 Fixed chain vs adaptive decomposition

Principle: one question decides it — can you enumerate the steps before starting? Yes → fixed prompt chain (cheaper, testable, deterministic: take it). No, because step 2 depends on what step 1 discovers → adaptive: map first, rank by impact, keep a plan that updates as dependencies surface.

Exam wrapper: "migrate off the deprecated ORM / add tests to a legacy codebase — entanglement unknown." The trap options decompose by what is already listable (files, directories) when the risk lives in what isn't (the dependency graph). Decompose around what you must discover.

TS 1.2 Context passing — subagents inherit nothing

Principle: a subagent starts with a fresh context window. It receives its own system prompt, the Task call's prompt string, and project CLAUDE.md — not the parent's conversation, not the parent's tool results, not a sibling's findings. The Task prompt string is the only channel, so the coordinator must paste in everything the subagent needs, as structured data so attribution survives.

Exam wrapper: "the implementation agent ignored the analysis agent's dependency report." First suspect, always: the report was never in its prompt. Distractors invent context eviction, prompt conflicts, or verbosity limits — none exist.

TS 1.3 Goal-oriented subagent prompts

Principle: tell a subagent what outcome and what quality bar — "cover all major subtopics, cite every claim with source and date" — not which steps in which order. A procedural script freezes the adaptability that justified spawning an agent: it can no longer follow a lead, skip a dead end, or loop back on a gap.

Exam wrapper: options that "help" by dictating the query sequence or pre-listing the URLs to fetch. They read as quality control; they are lobotomies.

TS 2.1 System-prompt keyword interference

Principle: tool selection is text-matching over names, descriptions, schemas — and the system prompt. An instruction like "always analyse documents thoroughly" quietly builds an association: requests containing "document" start flowing to whatever tool has "document" in its name, overriding perfectly good descriptions.

Exam wrapper: "descriptions look excellent, selection still misroutes on a keyword." Audit the system prompt for words that echo tool names. Distractors invent priority tables and manifest orderings — no such mechanisms exist.

TS 2.3 Role scoping and tool_choice

Principle: every tool an agent holds is a candidate answer to every selection it makes — 18 tools "for flexibility" is a measurably less reliable agent than 4–5 scoped to role. Unused tools are not free. Separately, tool_choice sets the floor: auto = may answer in prose; any = some tool, guaranteed; forced = that tool, guaranteed.

Exam wrapper: "grant everything so it never hits a wall" (kill it: scope to role, add narrow cross-role tools for the frequent 85% case), and "the pipeline crashed parsing a prose reply" (the auto hole — extraction never runs on auto).

TS 2.4 MCP config scope

Principle: one question — who is this server for? The team → project .mcp.json, committed, arrives on clone, secrets referenced as ${ENV_VAR} so each machine resolves its own. Just you / an experiment → user-scoped ~/.claude.json, never committed.

Exam wrapper: "works on the lead's machine, nowhere else" (it's in their user scope — move it, don't rewrite it) and "private repo, just inline the token" (a private repo is not a secrets store; ${ENV_VAR} is the pattern).
