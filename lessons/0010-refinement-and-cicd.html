Refinement & CI/CD

Two halves: how to steer Claude toward the output you actually wanted — and how to run it unattended in a pipeline, where nobody is there to steer at all.

Domain 3 Claude Code Configuration & Workflows · 20% Covers TS 3.5, TS 3.6 Time ~15 min

1. Iterative refinement: four named patterns

TS 3.5 names four techniques. Each solves a specific communication failure — knowing which failure each fixes is what the exam tests.

PatternThe failure it fixesHow
Concrete I/O examples Prose descriptions interpreted inconsistently 2–3 input → expected-output pairs; the transformation becomes unambiguous
Test-driven iteration "Improve it" loops that wander Write the test suite first — expected behaviour, edge cases, performance — then iterate by sharing failures
Interview pattern Requirements you didn't know you had Have Claude ask questions before implementing — surfacing cache invalidation, failure modes, constraints you hadn't considered
Batch vs sequential fixes Fixes that undo each other Interacting problems → one detailed message; independent problems → fix sequentially

Worked micro-examples of the two least obvious:

  • I/O examples. "Normalise the phone numbers" produced three inconsistent formats across runs. Show it: "(415) 555-0132" → "+14155550132", "07911 123456" → "+447911123456". Ambiguity gone — including the UK case the prose never mentioned. The blueprint's version: fixing null-handling in a migration script by giving a test case with example input and expected output.
  • Interacting vs independent. A pagination bug and an off-by-one in the same loop interact — fixing them one at a time invites each fix to break the other, so describe both in one message. A CSS typo and a broken API route are independent — sequential is cleaner, one verified fix at a time.
The common thread

Every pattern replaces redescription with evidence: examples instead of adjectives, failing tests instead of "still wrong", questions instead of assumed requirements. When an exam stem shows someone re-explaining in different words for the third time, the answer is whichever option introduces evidence.

2. CI/CD: running Claude Code unattended

The mechanics first — three flags, all verified, all tested on the exam TS 3.6:

# CI review job
claude -p "Review this diff against the criteria in CLAUDE.md" \
  --output-format json \
  --json-schema review-findings.schema.json
FlagWithout itWith it
-p / --print Job hangs forever waiting for interactive input Runs the prompt, prints to stdout, exits
--output-format json Prose a script must fragilely parse Machine-parseable output
--json-schema JSON of whatever shape Claude chose Output conforming to your schema — postable as inline PR comments

The official sample question is the hang: a pipeline runs claude "Analyze this PR" and freezes. Fix: -p. The distractors — --batch, CLAUDE_HEADLESS=true, redirecting stdin from /dev/null — are invented or wrong.

3. Context is what makes CI output good

Flags make CI work; context makes it useful. Three named practices, one per failure mode TS 3.6:

  • CLAUDE.md is the CI context channel. The pipeline's Claude knows nothing your prompt and repo don't tell it. Documenting testing standards, fixture conventions and review criteria in CLAUDE.md is how CI-invoked Claude learns what "good" means here — and it directly reduces low-value test generation.
  • Feed prior findings back. Re-running review after new commits? Include the previous findings and instruct: report only new or still-unaddressed issues. Otherwise every push re-posts the same comments, and developers learn to ignore the bot.
  • Show existing tests. Test generation without the current test files in context produces duplicates of scenarios already covered. Provide them, and ask for what's missing.

4. Don't review your own homework

The architectural point in TS 3.6, and a bridge to Domain 4: the session that generated code is measurably worse at reviewing it than a fresh instance. The generating session retains its own reasoning — the assumptions that produced the bug are still in context, actively defending it. An independent instance sees only the code.

Same session

"Now review what you just wrote" — the reviewer holds the generator's reasoning and is inclined to confirm it. Self-review instructions and extended thinking don't fix this; the contamination is the context itself.

Independent instance

A separate invocation with no generation context reviews the diff cold. In CI this is natural — the review job is a fresh claude -p call that never saw the code being written.
