Decomposition & Sessions

Two questions finish Domain 1. How do you split a task that is too big to do in one pass — and how do you come back to work an agent already did without paying for it twice?

Domain 1 Agentic Architecture & Orchestration · 27% Covers TS 1.6, TS 1.7 Time ~15 min

1. Two ways to decompose

When a task is too large for one pass, you split it. There are exactly two shapes, and TS 1.6 is about choosing between them.

Prompt chainingDynamic decomposition
ShapeA fixed sequential pipeline you define up front Subtasks generated from what each step discovers
You know…The steps before you startOnly the goal
SuitsPredictable multi-aspect workOpen-ended investigation
ExampleReview each file, then a cross-file pass "Add comprehensive tests to this legacy codebase"
TradesPredictable, testable, cheaper Adapts to what is actually there

The decision rule is simply: can you enumerate the steps in advance? If yes, chain them — you get determinism for free and you should take it. If the right second step depends on what the first step finds, no fixed pipeline can express that, and forcing one produces the narrow-decomposition failure from Lesson 02.

2. Prompt chaining: the review pattern

The exam's worked case: a pull request touches 14 files. A single pass over all of them produces detailed feedback on some, superficial comments on others, missed bugs, and contradictory findings — the same pattern flagged in one file and approved in another.

The cause is attention dilution, and the fix is a chain:

Pass 1..N each file, independently → local issues, consistent depth │ Pass N+1 all files together → cross-file data flow, integration bugs │ ▼ merged findings
The distractor that catches engineers

"Use a model with a larger context window." Wrong — and worth understanding why. Context window size governs how much fits. Attention dilution is about how evenly the model attends across what fits. All 14 files already fit; that was never the constraint. A bigger window changes nothing here.

3. Dynamic decomposition: the legacy case

"Add comprehensive tests to a legacy codebase" cannot be chained, because you do not yet know what is there. The blueprint's pattern TS 1.6 is three-phase:

  1. Map the structure — what modules exist, what depends on what.
  2. Identify high-impact areas — what is most used, most fragile, least covered.
  3. Build a prioritised plan that adapts as dependencies are discovered.

The word doing the work is adapts. Discovering that the payments module depends on an untested date utility should change the plan. A fixed pipeline written before step 1 could not have known the utility existed.

4. What a session actually is

A session is the accumulated conversation: your prompt, every tool call, every tool result, every response. The SDK writes it to disk, so you can return to it with full context — files already read, analysis already done.

Sessions persist the conversation, not the filesystem

This one sentence prevents several wrong answers. Returning to a session restores what the agent knew. It does not restore what the code was. If files changed in between, the session's memory of them is now a lie it does not know it is telling.

5. Continue, resume, fork

Fork
resume + fork_session		A specific ID Copies history into a new session; original untouched Exploring divergent approaches from one baseline

In the CLI this is --resume <session-name> for a named session. In the SDK, the ID comes from session_id on the result message; forking is fork_session=True (Python) / forkSession: true (TypeScript), passed alongside resume.

6. Fork: one analysis, several futures

The pattern TS 1.7: spend the expensive exploration once, then branch. An agent analyses a codebase — reads the modules, maps dependencies, forms an understanding. That baseline cost real tokens and time. Now you want to compare two refactoring approaches.

baseline session (codebase analysed — expensive) │ ┌────────┴────────┐ fork A fork B both start with the full analysis "refactor to "refactor to repositories" event sourcing" │ │ own id own id original stays untouched, resumable
Forking branches history, not files

If fork A edits a file, that edit is real and visible to fork B and to every other session in that directory. You have branched the conversation, not the working tree. For genuinely parallel exploration that writes code, isolate the filesystem too — separate worktrees or checkpointing.

7. When not to resume

The subtlest point in TS 1.7, and the one most likely to be tested: starting a new session with a structured summary is sometimes more reliable than resuming.

Resuming replays every stale tool result into context. If the code changed after that session ran, the agent now holds a confident, detailed, wrong picture — and stale specifics are worse than no specifics, because the model has no reason to doubt them.

Resume when…

Prior context is mostly still valid. You are following up on analysis, recovering from an interrupted run, or continuing a thread where nothing underneath moved.

Start fresh when…

Prior tool results are stale. The code moved on. Inject a structured summary of the conclusions — which are still true — and let the agent re-read what it needs.

There is a middle path worth knowing, because it is the cheapest of the three: resume, and tell the agent explicitly which files changed. It then re-reads those specific files rather than either trusting stale content or re-exploring everything from scratch.
