Domain 4 · Lesson 12 of 16

Criteria & Few-Shot

The schema fixed the shape. What's left is judgement: which findings to report, which cases to escalate, how to handle the ambiguous middle. The exam's position is blunt — vague adjectives don't transfer judgement; categorical criteria and worked examples do.

Domain 4 Prompt Engineering & Structured Output · 20% Covers TS 4.1, TS 4.2 Time ~15 min

1. Why "be conservative" doesn't work

A code-review bot floods PRs with nitpicks. The instinctive fix: add "be conservative — only report high-confidence findings" to the prompt. The blueprint states flatly that this fails to improve precision TS 4.1. Why?

"Conservative" and "high-confidence" are thresholds without a scale. The model has no calibrated internal dial these words adjust — it will produce output that sounds more hedged while flagging roughly the same things. You have changed the tone, not the boundary.

What moves the boundary is categorical criteria — naming the categories in and the categories out:

Vague dial

"Check that comments are accurate. Be conservative; only report issues you are highly confident about."

Categorical boundary

"Flag a comment only when its claimed behaviour contradicts the actual code behaviour. Report: bugs, security issues. Skip: minor style, patterns local to one file, naming preferences."

The left version asks the model to grade its own certainty — L01's unreliable proxy. The right version asks it to classify, which models do well. Report/skip lists, and a contradiction test instead of an accuracy vibe: every term is checkable against the code in front of it.

2. False positives are a trust problem

The blueprint's framing worth quoting: high false-positive categories undermine confidence in accurate categories. Developers don't evaluate a review bot finding by finding — they form one judgement of the bot. A security check that's right 95% of the time gets ignored because the style checker beside it cries wolf.

Two prescribed moves TS 4.1:

  • Temporarily disable a high-FP category to restore trust, and improve its prompt offline before re-enabling. A silent category costs less than a noisy wrong one.
  • Define severity with concrete code examples per level. "Critical / major / minor" without examples produces inconsistent classification; one worked example of each level anchors the scale.

3. Few-shot: examples as the specification of judgement

Explicit criteria set boundaries. But some cases sit on the boundary — and that is what few-shot examples are for TS 4.2. The blueprint's parameters:

  • 2–4 targeted examples, chosen from the ambiguous cases — not the easy ones. An example the model would get right anyway teaches nothing.
  • Each example shows the input, the decision, and the reasoning why that action beat the plausible alternative. The reasoning is the payload: it's what lets the model generalise to novel patterns instead of pattern-matching your exact cases.
  • Examples double as format demonstration — location, issue, severity, suggested fix — which is the named fix when detailed instructions still yield inconsistent output shapes.
<example>
Input: "I was double-charged and I want a refund NOW."
Decision: resolve (not escalate)
Why: anger is present but the issue is a standard duplicate-charge
     refund — within policy and agent authority. Sentiment alone
     is not an escalation trigger.
</example>

<example>
Input: "Your competitor sells this for $40 less. Match it or
        cancel my order."
Decision: escalate
Why: policy covers own-site price adjustments only. Competitor
     matching is a policy gap — escalate rather than improvise
     a commitment the business hasn't made.
</example>

Note what the pair teaches: the same-looking surface (an unhappy customer) splits on a principle (policy coverage), and the reasoning names it. That principle now transfers to cases neither example mentions.

4. Where few-shot is the named fix

The blueprint lists specific failure modes whose answer is few-shot examples — recognise them in stems TS 4.2:

FailureThe few-shot fix
Escalation miscalibration (easy cases escalated, hard ones attempted) Criteria + examples demonstrating escalate-vs-resolve on boundary cases
Inconsistent output format despite detailed instructions Examples demonstrating the exact desired shape
Review false positives on acceptable local patterns Examples distinguishing acceptable patterns from genuine issues
Extraction returning empty/null for fields present in oddly-formatted documents Examples showing correct extraction from varied structures — inline citations vs bibliographies, tables vs narrative
Hallucinated values on informal inputs ("about two and a half k") Examples demonstrating normalisation of informal measurements
Criteria vs examples vs enforcement — the full ladder

By now you have the whole toolkit, and the exam mixes them in one stem: invariant? → hook or gate (L03). Boundary you can state? → explicit categorical criteria. Boundary you can only show? → few-shot examples with reasoning. Most real systems need the second and third together — criteria draw the line, examples walk it.
