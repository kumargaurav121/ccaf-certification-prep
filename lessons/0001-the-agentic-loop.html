The Agentic Loop

An agent is not a special kind of model. It is an ordinary Messages API call placed inside a while loop, where one field in the response decides whether the loop runs again. Get that field right and everything else in Domain 1 follows.

Domain 1 Agentic Architecture & Orchestration · 27% Covers TS 1.1 Time ~15 min

1. What the model actually does

Claude cannot run anything. When you give it tools, it does not execute them — it emits a structured request that your code executes. That single fact is the whole architecture. The loop exists because the model must hand control back to you, receive the result, and then reason again with that result in front of it.

A tool definition has exactly three parts:

tools = [{
    "name": "lookup_order",
    "description": "Retrieve an order by its order ID. Returns status, "
                   "line items, totals and shipping dates.",
    "input_schema": {
        "type": "object",
        "properties": {
            "order_id": {"type": "string", "description": "e.g. ORD-12345"}
        },
        "required": ["order_id"]
    }
}]

The description is the only thing that tells Claude when to pick this tool over another. That is why Domain 2 spends an entire task statement on description quality — but we are getting ahead.

2. The round trip, concretely

You send a request. Claude replies with a message whose stop_reason is "tool_use" and whose content array contains a tool_use block:

{
  "stop_reason": "tool_use",
  "content": [
    {"type": "text", "text": "Let me look that up."},
    {"type": "tool_use",
     "id":   "toolu_01A09q90qw90lq917835lq9",
     "name": "lookup_order",
     "input": {"order_id": "ORD-12345"}}
  ]
}

You run the lookup yourself, then send the result back as a new user message containing a tool_result block. The tool_use_id must match the id from the block above — that is what pairs a result to its request:

{"role": "user", "content": [
    {"type": "tool_result",
     "tool_use_id": "toolu_01A09q90qw90lq917835lq9",
     "content": "{\"status\": \"delivered\", \"total\": 89.99}",
     "is_error": false}
]}
BlockDirectionKey fields
tool_useClaude → you id, name, input
tool_resultyou → Claude tool_use_id, content, is_error
The detail that trips people up

The assistant's turn must be appended to the conversation unchanged, including its tool_use block, before you append the tool_result. The history reads: user asks → assistant calls tool → user returns result → assistant reasons. Drop the assistant turn and the tool_use_id refers to nothing.

3. The loop itself

Here is the entire agentic loop. There is no more to it than this:

messages = [{"role": "user", "content": "Why was order ORD-12345 refunded?"}]

while True:
    response = client.messages.create(
        model="claude-opus-5", max_tokens=1024,
        tools=tools, messages=messages,
    )

    # 1. Always append the assistant's turn, verbatim.
    messages.append({"role": "assistant", "content": response.content})

    # 2. THE decision. Nothing else terminates the loop.
    if response.stop_reason != "tool_use":
        break

    # 3. Execute every tool_use block; collect every result.
    results = []
    for block in response.content:
        if block.type == "tool_use":
            results.append({
                "type": "tool_result",
                "tool_use_id": block.id,
                "content": run_tool(block.name, block.input),
            })

    # 4. Feed results back so the model can reason about them.
    messages.append({"role": "user", "content": results})
┌──────────────────────────────────────────────┐ │ │ ▼ │ send messages ──► Claude ──► stop_reason? │ │ │ "tool_use" ────┤ │ │ │ ├──► execute tools│ │ │ └──► append tool_result ─┘ "end_turn" ────► done — return the text

Note step 3 collects every tool_use block. Claude can request several tools in one turn, and they all belong in a single follow-up user message. Answering only the first is a real bug — the API rejects a turn with unmatched tool calls.

5. Why the anti-patterns are anti-patterns

The blueprint names three specific wrong ways to terminate the loop TS 1.1. Each fails for a mechanical reason worth understanding, not memorising.

Parsing text for a signal

Looping until the reply contains "done" or "final answer". Natural language is unconstrained — the model may say "I'm done searching" mid-investigation, or finish without ever saying it. You have replaced a typed field with a guess.

Read stop_reason

A closed enum the API guarantees. It is the only signal that means what it says.

An iteration cap as the mechanism

for i in range(5) as your termination logic. A task needing six tools is silently truncated; a task needing one wastes nothing but tells you nothing. The cap is not tracking whether the work finished.

A cap as a safety net

Keep a maximum to bound runaway cost — but stop_reason decides completion. Hitting the cap is an error path, not a success path.

Checking for text content

"If the response has a text block, it's finished." False: a turn can contain both a text block and a tool_use block — the example in section 2 does exactly that. Claude often narrates before calling a tool.

Ignore content shape entirely

Content tells you what to execute. stop_reason tells you whether to continue. Different questions.

6. Model-driven, not a decision tree

The last idea in TS 1.1 is conceptual. Because tool results re-enter the conversation, Claude chooses each next action with the previous results in context. A refund investigation might call lookup_order, discover the order was split across two shipments, and call it again for the second — a path nobody enumerated in advance.

That is the difference between an agent and a workflow. A pre-configured tool sequence is a workflow: predictable, cheaper, easier to test, and the right choice when the steps genuinely are fixed. An agent trades that predictability for the ability to adapt. The exam frequently asks you to choose between them, so hold both as legitimate.
