Structured Errors

An agent's tool will fail — the network drops, the input is malformed, policy says no. What the tool returns in that moment decides whether the agent retries intelligently, explains gracefully, escalates, or thrashes. "Operation failed" produces thrashing every time.

Domain 2 Tool Design & MCP Integration · 18% Covers TS 2.2 Time ~15 min

1. Errors are information for the model

The central inversion of this lesson: in ordinary software, errors flow to a handler. In an agent system, errors flow to a reasoning model that decides what to do next. That changes what an error message is for. It is not a log line — it is context the model reasons over, exactly like a successful result.

MCP encodes this with two distinct channels, and the split matters TS 2.2:

ChannelMechanismCoversWho sees it
Protocol errorJSON-RPC error object Unknown tool, malformed request, server fault Your client code
Tool execution errorNormal result with isError: true API failures, invalid input data, business rule violations The model itself
{
  "content": [{
    "type": "text",
    "text": "Failed to fetch weather data: API rate limit exceeded"
  }],
  "isError": true
}

Execution errors ride inside the result deliberately: the model must see them to self-correct. A protocol error never reaches the model; an isError result is the model's problem to solve — which is precisely why its content needs to be worth reasoning over.

2. The four error categories

The blueprint's taxonomy. What makes it useful is that each category implies a different correct next move — that is the whole point of classifying.

CategoryExampleRetry?The agent should…
TransientTimeout, service unavailable YesRetry, ideally with backoff — the world may differ in 2s
ValidationMalformed order ID, missing field Not as-isFix the input and call again — retrying unchanged input is waste
BusinessRefund window expired, policy violation NeverExplain to the user, offer alternatives — no retry will change policy
PermissionAgent lacks authority for this operation NeverEscalate to someone who has the authority

Now run the counterfactual: all four return "Operation failed". The model cannot tell a timeout from a policy violation, so it guesses — retrying the unretryable, apologising for the transient, escalating the trivially fixable. Uniform errors don't just lose information; they convert every failure into the same failure.

3. The structured error shape

What the blueprint expects a well-designed MCP tool to return on failure:

{
  "isError": true,
  "content": [{ "type": "text", "text": JSON.stringify({
    "errorCategory": "business",          // transient | validation | business | permission
    "isRetryable": false,                  // the explicit decision, precomputed
    "message": "Refund window expired: order ORD-12345 was delivered
                47 days ago; policy allows refunds within 30 days.",
    "customerExplanation": "I'm sorry — this order is outside our
                30-day refund window.",
    "alternatives": ["offer store credit", "escalate_to_human"]
  })}]
}
  • errorCategory — the classification, so the model doesn't infer it.
  • isRetryable — the retry decision made by the tool author, who knows; not by the model, which would guess. This flag is what prevents wasted retry loops.
  • Human-readable specifics — which rule, which values, so the model can explain.
  • Customer-friendly wording for business errors — the blueprint calls this out: the agent will relay policy refusals, so hand it wording fit to relay.
  • Alternatives — the same trick as L03's hook denial reason: name the door that is open, not just the one that closed.

4. Empty is not an error

The subtlest discrimination in TS 2.2, and a reliable exam target: an access failure and a valid empty result are different facts, and conflating them corrupts reasoning in both directions.

Valid empty result

search_orders("jane@x.com") ran successfully and found nothing. This is an answer: the customer has no orders. The agent should act on it — not retry, not apologise for a system problem that didn't happen.

Access failure dressed as empty

The database timed out, and the tool caught the exception and returned [] "to be safe". The agent now believes the customer has no orders. It will confidently tell them so. A recoverable failure has become plausible misinformation.

Silently suppressing errors — returning empty-marked-success — is one of the two named anti-patterns. The other is its mirror: terminating the whole workflow on a single failure, when the failure was recoverable or peripheral. Between suppression and collapse sits the correct behaviour: report the failure structurally and let the caller decide.

5. Recover local, propagate structured

In a multi-agent system, errors have a geography. The rule TS 2.2: handle locally what you can; propagate what you can't — with everything the coordinator needs to decide.

  • Local first: a subagent hitting a transient failure retries with backoff itself. The coordinator never hears about a timeout that resolved on the second attempt — that would be noise.
  • Propagate structured: when retries are exhausted, the subagent reports up: failure type, what was attempted, partial results gathered before the failure, and alternatives it can see.

Partial results are the piece engineers forget. A search agent that found six of ten sources before its API died has six sources. Propagating "search failed" throws them away; propagating structure lets the coordinator proceed with partial coverage and annotate the gap — which is exactly the pattern Domain 5 builds on later.

One instinct, three lessons

Notice this is the third appearance of the same principle: preserve structure across a boundary, because the other side cannot see what you saw. Hook denial reasons (L03), escalation handoffs (L03), and now error propagation. The exam tests it in all three costumes.
