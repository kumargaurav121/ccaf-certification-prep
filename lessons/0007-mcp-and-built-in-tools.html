1. What MCP actually is

The Model Context Protocol is an open standard for connecting agents to external systems. An MCP server wraps a system (Jira, Postgres, GitHub) and exposes capabilities in a form any MCP client can discover; Claude Code and the Agent SDK are clients. Two capability types matter for the exam:

MCP toolsMCP resources
AreActions the model can invokeContent the server exposes for reading
Thinkcreate_ticket, process_refund Issue summaries, doc hierarchies, database schemas
Exist toDo thingsShow what's available without tool calls

Discovery is automatic: when a session starts, tools from all configured servers are discovered at connection time and available simultaneously TS 2.4. Nothing routes between servers — the agent simply sees one large tool list. (Which is exactly why L05's tool-count concern applies across servers, not per server.)

The rule as the blueprint frames it: shared team tooling goes in project-scoped .mcp.json; personal or experimental servers go in user-scoped ~/.claude.json. Because .mcp.json is committed, teammates get the server on clone — and because that is a security surface, Claude Code asks each user to approve project-scoped servers before first use.

Credentials without committing secrets

// .mcp.json — committed to the repo
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"     // expanded from each
      }                                        // user's environment
    }
  }
}

Environment variable expansion (${GITHUB_TOKEN}) is the blueprint's named mechanism: the configuration is shared, the credential never is — each machine resolves the variable from its own environment TS 2.4.

3. Resources: the catalog pattern

Without resources, an agent asking "what documentation exists?" must make exploratory tool calls — list this, list that, fetch and see. Every probe costs a round trip and context. Resources exist to eliminate exploratory calls: the server exposes a catalog (issue summaries, schema listings, doc trees) that gives the agent visibility into what is available before it reaches for a tool.

The design instinct the exam wants: content that is browsed or referenced should be a resource; operations that change things or compute answers should be tools. A server that exposes get_all_issue_summaries as a tool is spending tool-selection budget (and a round trip) on what a resource would give for free.

4. Two adoption tradeoffs

Community server first

For standard integrations — Jira, GitHub, Postgres — choose existing community MCP servers over custom implementations. Reserve custom servers for genuinely team-specific workflows. Building a bespoke Jira wrapper is undifferentiated effort plus a maintenance tail.

Describe or be ignored

MCP tools compete with built-ins for selection. If your MCP server's search tool has a thin description, the agent will prefer built-in Grep over the more capable MCP tool — it can see exactly what Grep does. The fix is L05 applied here: enhance the MCP tool's description until its advantage is legible.

5. The built-in six

TS 2.5 is about picking the right primitive. The selection logic:

Need to search file contents?→Grep
Need to find files by name / path?→Glob
Need one file, fully, before reasoning?→Read
Need a surgical change at a unique anchor?→Edit
Need a new file or a full rewrite?→Write
Anything else — tests, builds, git?→Bash
ToolSearches / acts onReach for it when
GrepContents of files Finding a function's callers, an error message, an import
GlobPaths of files Finding files by name pattern — **/*.test.tsx
ReadOne file, fullyLoading content before reasoning or editing
EditTargeted change by unique anchor textSurgical modification
WriteWhole fileNew files, or full rewrites
BashAnything elseRunning tests, builds, git

Two tested subtleties:

  • The Edit fallback. Edit matches on unique anchor text. When the text you would anchor on is not unique in the file, Edit fails — the documented fallback is Read the full file, then Write it back modified. Not "try Edit harder", not Bash with sed.
  • Grep first means content-question; Glob first means name-question. "Where is calculateRefund called?" is a content question — Grep. "Where are the test files?" is a naming question — Glob. Mixing them up works eventually but wastes turns.

6. Exploring a codebase incrementally

The blueprint's exploration pattern, and the anti-pattern it replaces TS 2.5:

Incremental

Grep for entry points → Read to follow imports → trace the flow. Each step is guided by what the last step found; context carries only what the trail needed. For a re-exported function, first identify all exported names, then search for each across the codebase.

Read everything upfront

Reading all files "for context" floods the window with mostly-irrelevant content before the question is even sharp — the L02 isolation problem, self-inflicted. By the time the answer matters, the relevant file is buried in the middle of 60 others.
