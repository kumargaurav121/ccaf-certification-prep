Commands, Skills & Plan Mode

Three ways to package how your team works: commands for invocable prompts, skills for workflows with configuration, and plan mode for the decisions expensive enough to design before touching code. The exam tests where each lives and when each earns its cost.

Domain 3 Claude Code Configuration & Workflows · 20% Covers TS 3.2, TS 3.4 Time ~15 min

1. Slash commands: the scope rule again

A custom slash command is a prompt stored as a markdown file, invoked by name. The only structural question is the one you already know from L07 and L08 — who is it for? TS 3.2

ScopeLocationReaches teammates?
Project.claude/commands/review.md → /review Yes — version-controlled, arrives on clone/pull
User~/.claude/commands/review.md No — personal, all your projects

The official sample question is exactly this: "a /review command every developer should get when they clone the repo" → .claude/commands/ in the repository. The distractors were ~/.claude/commands/ (personal), CLAUDE.md (instructions, not commands), and a .claude/config.json commands array (does not exist).

2. Skills: workflows with configuration

A skill is a directory — .claude/skills/<name>/SKILL.md plus optional supporting files — whose YAML frontmatter configures how it runs TS 3.2:

---
name: analyze-codebase
description: Map the architecture of a package and report conventions.
context: fork              # run in an isolated subagent context
allowed-tools: Read Grep Glob   # tool access during the skill
argument-hint: "[package-path]" # autocomplete hint for arguments
---

1. Map the directory structure of $ARGUMENTS
2. Identify entry points, conventions, and dependencies
3. Return a structured summary

The three frontmatter fields the blueprint names, and what each is for:

FieldDoesReach for it when
context: fork Runs the skill in an isolated subagent context; only the result returns The skill produces verbose output (codebase analysis) or exploratory context (brainstorming) that would pollute the main conversation
allowed-tools Scopes tool access while the skill runs Limiting a skill to file reads so it cannot take destructive actions
argument-hint Shows expected parameters at invocation Developers keep invoking the skill without the arguments it needs

Recognise context: fork? It is L02's context isolation, packaged: the forty files a codebase-analysis skill reads stay in the fork; the main session receives only the summary. Same architecture, one line of YAML.

One more TS 3.2 fact: to personalise a team skill without affecting anyone else, create a variant in ~/.claude/skills/ under a different name — same-named personal skills would shadow confusingly; a distinct name keeps both invocable.

3. Skills vs CLAUDE.md: the boundary

CLAUDE.md / rules

Always-loaded universal standards. Facts and conventions that should shape every session without anyone asking: naming, build commands, architecture. If it must apply automatically, it lives here (or in a path-scoped rule).

Skills

On-demand, task-specific workflows. Multi-step procedures invoked when needed: deploy checklist, release notes, codebase analysis. Loads only when used — long reference material costs nothing until invoked.

The tell in exam stems: "should apply automatically whenever…" → CLAUDE.md or a path-scoped rule. "The team runs this when they need to…" → a skill or command. A procedure pasted into CLAUDE.md burns context in every session that never uses it.

Product note (know both, answer the exam's version)

In current Claude Code, commands have merged into skills — .claude/commands/deploy.md and .claude/skills/deploy/SKILL.md both create /deploy, and old command files keep working. The exam treats commands and skills as distinct mechanisms with the locations above — answer in those terms.

4. Plan mode vs direct execution

TS 3.4 is a cost-of-error judgement. Plan mode explores and designs without making changes; direct execution just goes. The decision:

Signal in the taskModeWhy
Architectural decisions — service boundaries, module dependencies PlanWrong structure discovered late = costly rework
Large-scale change — a migration touching 45+ files PlanScope must be understood before the first edit
Multiple valid approaches with different tradeoffs PlanThe choice is the work; design it explicitly
Single-file bug fix with a clear stack trace DirectScope is already known; planning is overhead
Adding one validation check to one function DirectWell-scoped, low blast radius

Two refinements the exam rewards:

  • Plan then execute is one workflow, not two choices. The canonical pattern for a library migration: plan mode to explore and design the approach, then direct execution to implement the planned change. The official sample's wrong answer worth remembering: "start direct and switch to plan mode if it gets complex" — wrong because the complexity is already stated in the task; you don't wait to discover what you were told.
  • The Explore subagent handles verbose discovery: during multi-phase work, delegating "find every usage of X" to Explore keeps hundreds of grep hits out of the main context, returning summaries instead. L02's isolation, again — this time built in.
