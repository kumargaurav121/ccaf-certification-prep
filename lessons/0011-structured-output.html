Structured Output

"Please respond in JSON" is a request. A tool schema is a contract. The trick at the heart of Domain 4: you don't ask Claude to write JSON — you define a tool whose input is your schema, and let the tool-calling machinery guarantee the shape.

Domain 4 Prompt Engineering & Structured Output · 20% Covers TS 4.3 Time ~15 min

1. The extraction-tool trick

Prompting for JSON in a text response fails in familiar ways: a chatty preamble before the brace, a trailing comma, markdown fences around the payload. Parsing prose-adjacent JSON is a tax you pay on every call.

The reliable approach TS 4.3 inverts it. Define a tool whose input_schema is the shape you want, and read the data out of the tool_use block's input:

tools = [{
    "name": "record_invoice",
    "description": "Record the structured data extracted from an invoice.",
    "input_schema": {
        "type": "object",
        "properties": {
            "invoice_number": {"type": "string"},
            "vendor":         {"type": "string"},
            "total":          {"type": "number"},
            "due_date":       {"type": ["string", "null"],
                               "description": "ISO 8601; null if not stated"},
            "category": {
                "enum": ["utilities", "software", "travel", "other"]
            },
            "category_detail": {"type": ["string", "null"],
                               "description": "Required when category is 'other'"}
        },
        "required": ["invoice_number", "vendor", "total"]
    }
}]

response = client.messages.create(
    model="claude-opus-5", max_tokens=1024,
    tools=tools,
    tool_choice={"type": "tool", "name": "record_invoice"},
    messages=[{"role": "user", "content": f"Extract from:\n{document}"}],
)
data = next(b for b in response.content if b.type == "tool_use").input

The tool doesn't exist. Nothing executes. record_invoice is a schema wearing a tool costume — the "call" is the output. And because tool arguments are generated under the schema, JSON syntax errors are eliminated: no fences, no preamble, no trailing commas. Add strict: true to the definition and conformance to the schema is guaranteed exactly.

2. What the schema cannot do

The line the exam draws

Schemas eliminate syntax errors, not semantic ones. A response can validate perfectly and still be wrong: line items that don't sum to the stated total, a billing address in the shipping field, a date that exists nowhere in the document. The schema checks shape; it cannot check truth.

This distinction runs the whole domain. Syntax errors → solved structurally, by tool use. Semantic errors → need validation after extraction and retry loops with error feedback — which is Lesson 13. If an exam option claims a stricter schema will fix values landing in the wrong fields, it is wrong; that failure validates fine.

3. tool_choice for extraction

You met the mechanics in L05; here is how they map to extraction pipelines TS 4.3:

SituationSettingWhy
One known document type Forced: {"type":"tool","name":"record_invoice"} That schema, every time — no discretion needed
Several schemas, document type unknown {"type":"any"} Structured output guaranteed; the model picks which schema fits
A specific step must run first Forced on that step, then relax e.g. extract_metadata before enrichment tools

The hole auto leaves open, one more time: the model may return conversational text with no tool call, and a pipeline that parses tool_use blocks crashes. Extraction pipelines never run on auto.

4. Nullable fields: the anti-hallucination device

The subtlest and most-tested schema decision. Mark a field required and non-nullable, and you have ordered the model to produce a value — even when the document doesn't contain one. The model complies the only way it can: it fabricates something plausible.

Required everywhere

"due_date" required, non-nullable. Invoice has no due date. The model invents one — plausible, well-formatted, validating, and false. The schema manufactured the hallucination.

Nullable where absence is possible

"type": ["string", "null"] with "null if not stated" in the description. Absence now has a legal representation, and the model uses it. Truly-always-present fields stay required.

Two companion patterns from the blueprint:

  • Enum + "other" + detail string. A closed enum forces every oddball into the nearest wrong bucket. Adding "other" plus a category_detail field keeps categories extensible without losing information — and an "unclear" value gives genuinely ambiguous cases an honest home instead of a coin flip.
  • Normalisation rules ride in the prompt, not the schema. Source documents write dates five ways; the schema wants ISO 8601. JSON Schema cannot express "convert '3rd March 26' to 2026-03-03" — so format rules go in the prompt alongside the strict schema. Prompt handles messy input; schema locks clean output.
Where this goes next

The schema now guarantees shape and honest absence. What it can't guarantee — precision, consistency, judgement on ambiguous cases — is prompt work: explicit criteria and few-shot examples. That's Lesson 12.
