Tool Interfaces & Selection

Claude never sees your tool's code. It sees a name, a description and a schema, and it chooses from those alone. That makes the description the most load-bearing string in your system — and most selection bugs are description bugs wearing a disguise.

Domain 2 Tool Design & MCP Integration · 18% Covers TS 2.1, TS 2.3 Time ~15 min

1. How selection actually works

When a request arrives, Claude reads every tool's name, description and input_schema, and matches the request against that text. There is no other channel. No routing table, no training on your tools, no memory of which tool worked last time. Descriptions are the primary mechanism LLMs use for tool selection TS 2.1 — which means:

  • Minimal descriptions ("Retrieves customer information") give the model nothing to discriminate with when two tools look similar.
  • Overlapping descriptions cause misrouting even when each is individually fine.
  • Fixing descriptions is free, immediate, and the correct first move — before few-shot examples, before routing layers, before consolidation.

2. Anatomy of a description that selects reliably

The blueprint names four ingredients. Written out for the exam's own support-agent tools:

"name": "lookup_order",
"description":
  "Retrieve one order's status, line items, totals and shipping dates.

   Input: an order ID in the format ORD-XXXXX (e.g. ORD-12345).
   Example queries this serves: 'where is my order', 'was ORD-2231
   delivered', 'what did I pay for order X'.

   Edge cases: returns the most recent state only; historical
   snapshots are not available. Split shipments appear as one order
   with multiple shipping dates.

   Use lookup_order when you already have an order ID.
   Use get_customer first when you only have a name or email —
   this tool cannot search by customer."
IngredientAnswers the model's question
Input formats"Can I call it with what I have in hand?"
Example queries"Does this request look like that tool's requests?"
Edge cases"What will I get back in the awkward cases?"
Boundaries vs similar tools"Why this one and not its neighbour?"

Anthropic's engineering guidance adds the framing worth remembering: write the description as you would explain the tool to a new team member, making implicit context explicit — and prefer unambiguous parameter names (user_id, never user).

3. The overlap failure, and its three fixes

The blueprint's worked example: analyze_content and analyze_document, near-identical descriptions. The agent routes web results to the document tool and PDFs to the content tool, apparently at random — because from where the model sits, the two are random. Three escalating fixes TS 2.1:

  1. Rewrite the descriptions to state each tool's boundary explicitly. Cheapest, first.
  2. Rename to eliminate conceptual overlap — analyze_content becomes extract_web_results with a web-specific description. The name itself now carries selection signal.
  3. Split a generic tool into purpose-specific tools — analyze_document becomes extract_data_points, summarize_content, verify_claim_against_source, each with a defined input/output contract.
The fourth suspect: your system prompt

Selection is also steered by the system prompt, and keyword-sensitive instructions can override well-written descriptions. An instruction like "always analyze documents thoroughly" builds an unintended association: requests containing the word "document" start flowing to whatever tool has "document" in its name. When selection misbehaves and the descriptions look right, audit the system prompt for keywords that echo tool names.

4. How many tools? Fewer than you think

TS 2.3 is blunt: an agent with 18 tools selects less reliably than an agent with 4–5, purely because every additional tool enlarges the discrimination problem. Two corollaries:

  • Scope tools to role. A synthesis agent with web-search tools will eventually use them — badly. Agents misuse tools outside their specialisation not out of malice but because the tools are there, occupying selection probability.
  • Consolidate when it reduces agent burden. Anthropic's example: one schedule_event that finds availability internally beats list_users + list_events + create_event — the agent makes one decision instead of orchestrating three. Consolidation and splitting are both valid; the test is always which gives the model fewer, clearer decisions.

Two named patterns from the blueprint complete the picture:

Constrained alternative

Replace a generic fetch_url with load_document that validates document URLs. The narrower contract prevents whole categories of misuse without any prompt text.

Scoped cross-role tool

The synthesis agent gets a narrow verify_fact for the 85% of simple checks; complex investigation still routes through the coordinator. Least privilege, sized to the common case.

5. tool_choice: dialling model discretion

Everything so far improves the model's judgement. tool_choice removes judgement where you don't want any TS 2.3:

SettingGuaranteesCanonical use
{"type": "auto"}Nothing — model may answer in text Conversation where a tool may not be needed
{"type": "any"}Some tool will be called Structured output when the right schema depends on the document
{"type": "tool", "name": "extract_metadata"}That exact tool is called Forcing a first step before enrichment runs in later turns

The distinction the exam leans on: auto means a request can come back as conversational text with no tool call at all. If your pipeline parses tool output, that is a crash. any closes that hole while leaving the choice of tool open; forced selection closes both.
