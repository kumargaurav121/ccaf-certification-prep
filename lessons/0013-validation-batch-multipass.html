Validation, Batch & Multi-Pass

L11 ended with a warning: schemas can't catch semantic errors. This lesson is what catches them — validation loops that feed errors back, batch processing that matches cost to latency tolerance, and review architectures that don't trust a model to grade its own homework.

Domain 4 Prompt Engineering & Structured Output · 20% Covers TS 4.4, TS 4.5, TS 4.6 Time ~15 min

1. Retry with error feedback

An extraction fails Pydantic validation. The naive retry re-sends the same request — same input, same instructions — and mostly gets the same failure. The blueprint's pattern TS 4.4 makes the retry a correction, not a re-roll. The follow-up request contains three things:

  1. The original document — the ground truth, again.
  2. The failed extraction — what the model produced.
  3. The specific validation errors — "line_items sum to 847.50 but stated_total is 874.50"; "due_date is '2026-13-01', month out of range".

Now the model can diagnose: compare its own output against the source with the error pointing at the discrepancy. Same machinery as L10's test-driven iteration — evidence instead of repetition.

2. When retries cannot work

The discrimination the exam tests

Retries fix format and structural errors — the information was in the document and came out wrong. Retries cannot fix absence — if the PO number exists only in a separate purchase order you never provided, no number of retries will produce it. Each one either returns null (correct, and retrying was waste) or fabricates (worse). Before retrying, ask: is the information actually in what I sent?

Two self-correction designs the blueprint names for catching semantic errors structurally TS 4.4:

  • Extract calculated_total alongside stated_total — make the model compute the sum of line items as its own field, and a mismatch between the two becomes machine-detectable without re-reading the document.
  • conflict_detected booleans — when the source itself is inconsistent (two different totals printed), give the model a way to say so rather than silently picking one. The nullable-field lesson again: honest signals need a legal representation.
  • detected_pattern fields on review findings — record which code construct triggered each finding, so when developers dismiss findings you can analyse false-positive patterns systematically instead of anecdotally. This is the feedback loop that feeds L12's category-disabling decision.

3. The Message Batches API: a latency-tolerance question

The facts, fixed TS 4.5:

PropertyValue
Cost50% cheaper
Processing windowUp to 24 hours
Latency SLANone
Correlationcustom_id on each request/response pair
Multi-turn tool callingNot supported — no executing tools mid-request

The decision is one question: is anything blocked while this runs? A developer waiting at a merge gate — blocked, synchronous API, no argument. A technical-debt report read tomorrow morning — nobody waits, batch, take the 50%. "Batches often finish faster than 24h" is true and irrelevant: often is not a guarantee you can put in front of a human who is waiting.

Three operational skills around it:

  • SLA arithmetic. Guaranteeing a 30-hour turnaround with a 24-hour processing window means submitting batches at least every 4–6 hours — the submission cadence, not the processing window, is your design variable.
  • Failure handling by custom_id. When 7 of 100 documents fail, resubmit only those seven — identified by custom_id — with modifications that address why they failed (e.g. chunking the ones that exceeded context). Resubmitting all 100 doubles cost for nothing.
  • Refine on a sample first. Before batch-processing 10,000 documents, tune the prompt on a small sample synchronously. First-pass success rate is the lever on total cost — iterating via 24-hour round trips is the most expensive possible way to debug a prompt.

4. Multi-pass and multi-instance review

Two independent findings about review quality, both from TS 4.6:

Split by scope: per-file + integration

Large reviews in one pass produce attention dilution — inconsistent depth, missed bugs, contradictory verdicts on identical code. Split: per-file passes catch local issues at consistent depth; a separate integration pass examines what per-file passes structurally cannot — cross-file data flow, mismatched assumptions between modules, contract violations at boundaries.

Split by instance: generator ≠ reviewer

A model retains its generation reasoning in context and won't effectively question its own decisions in the same session — self-review instructions and extended thinking don't remove the contamination. An independent instance with no generation context reviews cold. (You met this in CI form in L10; here it's the general architecture.)

One nuance that looks like a contradiction until you see the structure: the blueprint endorses verification passes where the model self-reports confidence alongside each finding — to enable calibrated review routing. Haven't we spent three lessons saying self-reported confidence is an unreliable proxy? The difference is what consumes it:

  • Confidence as an autonomous trigger ("escalate when confidence < 7") — rejected; the number is uncalibrated and the model is confidently wrong exactly on the hard cases.
  • Confidence as routing input, calibrated against labelled data — endorsed; you measure what 0.9 actually means against a validation set before letting it route anything. The calibration machinery is Lesson 16.
