Configuration Hierarchy

You use CLAUDE.md every day — but the exam probes the machinery underneath: which file loads when, what @import actually does and doesn't do, and when a glob-scoped rule beats a directory file. This is where daily fluency meets exam-grade precision.

Domain 3 Claude Code Configuration & Workflows · 20% Covers TS 3.1, TS 3.3 Time ~15 min

1. The three levels, and who each serves

LevelLocationApplies toShared with team?
User~/.claude/CLAUDE.md All your projectsNo — never in version control
Project./CLAUDE.md or ./.claude/CLAUDE.md Everyone in this repoYes — committed
Directory<subdir>/CLAUDE.md Work touching that subtreeYes — committed

Two loading behaviours the exam expects you to know precisely TS 3.1:

  • Files at and above the working directory load at launch, ordered root-down, so more specific instructions are read last. All levels concatenate — nothing overrides anything.
  • Subdirectory CLAUDE.md files load on demand — only when Claude reads files in that subtree. They cost no context until relevant.
The diagnostic scenario the exam reuses

A new teammate clones the repo and Claude ignores "the team's" conventions — because those conventions live in someone's user-level ~/.claude/CLAUDE.md, which is not in version control and never reaches teammates. Anything the team must share belongs at project level. The fix is a move, not a rewrite.

2. @import: modularity, not context savings

A CLAUDE.md can reference other files with @path syntax TS 3.1:

See @README for the project overview.

# Standards
- API conventions: @docs/api-standards.md
- Git workflow:    @docs/git-instructions.md
- Personal prefs (cross-worktree): @~/.claude/my-prefs.md

The mechanics that get tested:

  • Relative paths resolve relative to the file containing the import, not the working directory. Imports recurse to a maximum depth of four hops.
  • Imported files are expanded at launch — so @import organises content; it does not reduce context consumption. If the goal is loading less, you want path-scoped rules (below).
  • A path inside backticks (`@README`) is literal text, not an import.
  • The blueprint's use case: each package's CLAUDE.md imports only the standards files relevant to that package, chosen by the maintainer who knows the domain.

3. .claude/rules/: split the monolith

A 600-line CLAUDE.md is a real failure mode — adherence drops as the file grows. The structured fix is topic files in .claude/rules/ TS 3.1:

.claude/
├── CLAUDE.md            # short: identity, build commands, pointers
└── rules/
    ├── testing.md
    ├── api-conventions.md
    └── deployment.md

A rule file without frontmatter loads at launch, same priority as .claude/CLAUDE.md — you have gained organisation, not laziness. The laziness comes from the paths field.

4. Path-scoped rules: load only what the work touches

Add YAML frontmatter with glob patterns, and the rule loads only when Claude reads a file matching them TS 3.3:

---
paths:
  - "terraform/**/*"
  - "**/*.test.{ts,tsx}"
---

# Rules that apply only to matching files
- Never hardcode region names; use var.region
- Test files use the arrange / act / assert layout
  • Irrelevant conventions stay out of context — less noise, fewer tokens, better adherence on what does load.
  • Globs match by pattern, not location: **/*.test.tsx catches every test file wherever it lives.
  • Brace expansion works: src/**/*.{ts,tsx}.

The discrimination the exam actually tests

Path-scoped rule wins when…

The convention follows a file type spread across the tree. Test files sit next to the code they test — Button.test.tsx beside Button.tsx — in dozens of directories. One glob rule covers all of them.

Directory CLAUDE.md wins when…

The convention belongs to a place: everything under packages/api/ uses async/await error handling. If the boundary is a subtree, a file in that subtree is the natural home.

Notice the failure if you choose wrong: covering scattered test files with directory CLAUDE.md files means one file per directory that contains tests — dozens of copies to keep in sync. That maintenance burden is the tell in exam stems.

5. Diagnosing with /memory

The blueprint names one diagnostic skill TS 3.1: when behaviour is inconsistent across sessions or teammates, run /memory to see which memory files exist and are loaded, and edit them from there. The typical finds:

  • An instruction living at user level that everyone assumed was project level.
  • Two files giving contradictory guidance — Claude picks one arbitrarily.
  • A rule whose glob never matches the files it was meant for.

(In current builds, /context additionally shows what actually loaded into this session — useful, but /memory is the command the exam names.)

One mental model for the whole lesson

Every mechanism here answers one question: who needs this instruction, and when? Everyone always → project CLAUDE.md. Just you → user level. Only when touching certain files → path-scoped rule. Only in one subtree → directory CLAUDE.md. Only on demand for a task → that's a skill, which is Lesson 09.
