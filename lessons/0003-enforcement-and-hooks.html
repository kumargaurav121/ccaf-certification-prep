Enforcement & Hooks

A prompt is a request. A hook is a guarantee. Knowing which of those a given business rule requires is the most frequently tested judgement in Domain 1 — and the answer is not always "hook".

Domain 1 Agentic Architecture & Orchestration · 27% Covers TS 1.4, TS 1.5 Time ~15 min

1. Probabilistic versus deterministic compliance

Everything in this lesson descends from one fact: a system prompt instruction has a non-zero failure rate. Not a high one. But if you tell an agent "always verify the customer before issuing a refund", it will comply almost always — and "almost always" is a different engineering category from "always".

The blueprint puts it plainly TS 1.4: when deterministic compliance is required, prompt instructions alone are insufficient. Whether 99% compliance is acceptable depends entirely on what the 1% costs.

Prompt-based guidanceProgrammatic enforcement
MechanismSystem prompt, few-shot examplesHooks, prerequisite gates
ComplianceProbabilisticDeterministic
HandlesJudgement, tone, boundaries, prioritiesInvariants, sequences, thresholds
Cost of failure it suitsRecoverable — a slightly worse answerUnrecoverable — money moved, data deleted
The test to apply

Ask: can I write a deterministic check for this? "Has get_customer returned a verified ID?" — yes, that is a boolean. Enforce it. "Is this case too complex to handle autonomously?" — no, that is a judgement with no checkable definition. Teach it with criteria and examples instead.

Reaching for a hook where judgement is required does not make the judgement deterministic; it just moves the guesswork into your code.

2. Prerequisite gates

The canonical example, straight from the exam's support scenario: production data shows the agent sometimes calls lookup_order using only a customer's stated name, skipping get_customer — and occasionally refunds the wrong account.

A prerequisite gate blocks downstream tool calls until an upstream step has completed TS 1.4:

agent wants: process_refund(order_id, amount) │ ▼ ┌───────────────────────┐ │ PreToolUse gate │ has get_customer returned │ verified_customer_id? │ a verified ID this session? └───────────┬───────────┘ no ───┴─── yes │ │ DENY + reason ALLOW → tool runs │ model sees the denial reason and calls get_customer first instead

Note what the denial does: it does not crash. The block returns a reason, the model reads it, and self-corrects by calling the prerequisite. You are constraining the space of legal actions, not fighting the model.

3. Hooks: the mechanism

Hooks are callbacks that run your code at fixed points in the agent lifecycle. Two matter for the exam TS 1.5:

EventFiresCanExam use
PreToolUseBefore a tool runsBlock or modify the call Enforce policy — block refunds over $500 and redirect to escalation
PostToolUseAfter a tool returnsTransform the result Normalise heterogeneous data before the model reads it

Hooks are registered per event with a matcher on the tool name. MCP tools match the pattern mcp__<server>__<action>.

Blocking with PreToolUse

async def block_large_refunds(input_data, tool_use_id, context):
    if input_data["tool_name"] == "process_refund":
        if input_data["tool_input"]["amount"] > 500:
            return {"hookSpecificOutput": {
                "hookEventName": "PreToolUse",
                "permissionDecision": "deny",
                "permissionDecisionReason":
                    "Refunds above $500 require human approval. "
                    "Use escalate_to_human with a handoff summary.",
            }}
    return {}

options = ClaudeAgentOptions(
    hooks={"PreToolUse": [HookMatcher(matcher="process_refund",
                                      hooks=[block_large_refunds])]}
)

permissionDecision takes "allow", "deny", "ask" or "defer". When several hooks apply, deny beats defer beats ask beats allow — any single deny blocks the operation. A PreToolUse hook can also rewrite the call via updatedInput rather than refusing it outright.

Normalising with PostToolUse

The blueprint's example: your MCP tools come from different backend teams. One returns Unix timestamps, one ISO 8601, one numeric status codes. The agent now has to reason across three formats, and it will occasionally get it wrong.

Fixing this in the prompt is the wrong instinct — you would be asking the model to do deterministic data conversion on every turn, forever, at some error rate. A PostToolUse hook converts the result before the model ever sees it, using updatedToolOutput to replace the output (or additionalContext to append to it).

Prompt-based

"Note that get_orders returns Unix timestamps while lookup_shipment returns ISO 8601. Convert as needed." Burns tokens every turn, and fails occasionally forever.

Hook-based

One PostToolUse hook normalises every timestamp to ISO 8601. The model sees one format and never knows there was a problem. Correct 100% of the time.

4. Structured handoff on escalation

When an agent escalates mid-process, the human receiving it has no access to the conversation transcript TS 1.4. A handoff that says "customer is unhappy about a refund" forces that human to redo the entire investigation.

A structured handoff carries what the investigation already established:

{
  "customer_id": "CUS-88213",
  "root_cause": "Duplicate charge from a retried payment webhook",
  "amount": 149.98,
  "verified": true,
  "steps_taken": ["identity verified", "both charges confirmed in ledger"],
  "recommended_action": "Refund the duplicate charge of $74.99",
  "escalation_reason": "Amount exceeds agent authority threshold"
}

This is the same instinct as the PostToolUse normaliser and, later, structured error responses: preserve structure across a boundary, because whoever is on the other side cannot see what you saw.

5. Multi-concern requests

One more TS 1.4 skill, easily missed. Real customers send messages containing several problems at once: "my order arrived damaged, I was charged twice, and I want to change my address."

The pattern is decompose → investigate in parallel using shared context → synthesise one unified resolution. Not three separate replies, and not one blurred reply that half-answers everything. Note this reuses the parallel tool-call mechanics from Lesson 02: independent investigations issued together, results merged afterwards.
