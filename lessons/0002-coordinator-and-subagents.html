Coordinator & Subagents

A subagent is not a function call. It is a second agentic loop running in a context your coordinator cannot see, connected by exactly one string of text. Almost every multi-agent bug follows from forgetting that sentence.

Domain 1 Agentic Architecture & Orchestration · 27% Covers TS 1.2, TS 1.3 Time ~15 min Builds on L01

1. Why spawn a second agent at all

Not for parallelism first — for context isolation. A subagent that reads forty files to answer "where is the refund flow defined?" burns forty files of context. If it runs inside your main loop, that content stays in the conversation forever, crowding out everything after it. If it runs as a subagent, the parent receives only the final answer. The forty file reads never touch the parent's context window.

Three further benefits follow: parallelism (independent subtasks finish in the time of the slowest, not the sum), specialised instructions (a migration expert's system prompt would be noise in the main agent), and tool restriction (a reviewer that only has Read and Grep cannot accidentally write).

2. What a subagent actually is

It is the loop from Lesson 01, run again, with a fresh conversation. It calls tools, gets results, iterates on stop_reason, and terminates on end_turn. The only thing that returns to the parent is its final message — delivered as a tool result.

COORDINATOR (its own loop, own context) │ ┌────────────┼────────────┐ │ │ │ Task Task Task ← one response, three calls = parallel │ │ │ ┌───▼───┐ ┌───▼───┐ ┌───▼───┐ │search │ │analyse│ │ synth │ each: fresh context, own loop └───┬───┘ └───┬───┘ └───┬───┘ │ │ │ final msg final msg final msg ← ONLY this returns │ │ │ └────────────┼────────────┘ ▼ COORDINATOR aggregates ✗ subagents never talk to each other directly

3. What crosses the boundary — and what does not

This table is the single highest-value thing in the lesson. TS 1.3

The subagent receives

  • Its own system prompt (AgentDefinition.prompt)
  • The Task tool's prompt string — the only channel from the parent
  • Project CLAUDE.md
  • Its tool definitions

It does not receive

  • The parent's conversation history
  • The parent's tool results
  • The parent's system prompt
  • Anything from a sibling subagent
  • Anything from a previous invocation of itself
The consequence you are tested on

If the synthesis agent needs the search agent's findings, the coordinator must copy those findings into the synthesis agent's prompt. There is no shared memory, no automatic inheritance, no ambient context. "Summarise what the other agents found" fails, because the synthesis agent has never seen what the other agents found.

This is also why structured output between agents matters. If the search agent returns prose, the coordinator has to paste prose into the next prompt and attribution dissolves. If it returns {claim, evidence, source_url, published_date}, the coordinator can pass content and metadata through intact — which is what makes cited reports possible.

4. Spawning: the mechanics

Subagents are spawned through the Task tool, and the coordinator's allowedTools must include "Task" or the invocation is never approved and Claude quietly does the work itself instead.

options = ClaudeAgentOptions(
    allowed_tools=["Read", "Grep", "Glob", "Task"],   # <-- Task required
    agents={
        "web-searcher": AgentDefinition(
            description="Searches the web for primary sources on a topic.",
            prompt="You find primary sources. Return claim, excerpt, "
                   "source URL and publication date for each finding.",
            tools=["WebSearch", "WebFetch"],   # scoped: cannot write files
            model="sonnet",
        ),
    },
)
FieldRequiredWhat it does
descriptionyesWhen to use this subagent — this is how Claude decides to delegate

Exam answer vs shipping product

The Exam Guide says Task. Answer Task on the exam. In the current product the tool was renamed to Agent (Claude Code v2.1.63) — SDKs now emit "Agent" in tool_use blocks while still listing "Task" in system:init. Your daily-driver instinct will say Agent; the exam wants Task.

5. Parallel means one response, not one turn each

To run subagents concurrently, the coordinator emits multiple Task tool calls in a single response. Exactly as in Lesson 01: several tool_use blocks in one turn, all answered together in one follow-up message.

Parallel

One assistant turn containing three Task calls. All three subagents run concurrently; wall-clock is the slowest one.

Accidentally sequential

Three assistant turns, one Task call each. Each waits for the last. Wall-clock is the sum. Functionally identical, three times slower.

6. Hub-and-spoke: why everything routes through the coordinator

TS 1.2 The coordinator manages all inter-subagent communication, error handling and information routing. Subagents never talk to each other. Three reasons, and the exam expects you to be able to give them:

  • Observability. One place to see what was delegated, what came back, what failed.
  • Consistent error handling. A subagent timeout is handled by one policy, not by whichever peer happened to be listening.
  • Controlled information flow. The coordinator decides what each subagent sees — which is the only lever you have, given section 3.

7. The coordinator's real job

Delegation is the easy part. The coordinator owns four responsibilities, and the exam tests the failure mode of each.

ResponsibilityDone badlyDone well
Task decomposition Decomposes "creative industries" into digital art, graphic design, photography — and the report silently omits music, writing and film Partitions scope to cover the topic, assigning distinct subtopics or source types to minimise duplication
Dynamic selection Always routes through the full pipeline regardless of what was asked Analyses the query and invokes only the subagents it actually needs
Result aggregation Concatenates final messages, losing which agent found what Merges structured findings, preserving claim–source mappings
Iterative refinement One pass: delegate, synthesise, ship Evaluates synthesis for gaps, re-delegates with targeted queries, re-invokes synthesis until coverage is sufficient
Narrow decomposition is the signature Domain 1 failure

Every subagent can execute perfectly and the system still fails, because the fault is in what they were asked to do. When a multi-agent system produces confident, coherent, incomplete output, suspect the decomposition before you suspect any subagent.

8. Write goals, not procedures

A last point that is easy to get backwards. Coordinator prompts should specify research goals and quality criteria — not step-by-step procedural instructions.

Procedural

"Call web-searcher. Then call doc-analyser on each result. Then call synthesiser." You have hard-coded a pipeline into a system whose value is adapting to what it finds. The coordinator can no longer skip a step or loop back.

Goal + criteria

"Produce a cited report covering all major sub-domains of the topic. Every claim needs a source and a date. Identify coverage gaps and investigate them before synthesising." Now the coordinator can decompose, re-delegate and stop when the criteria are met.
